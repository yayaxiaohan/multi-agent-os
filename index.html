Subspace-Aligned Multi-Agent Architecture

A specification for recursive multi-agent systems
grounded in the geometry of LLM knowledge representation

Abstract. We present seven implementation-free principles for designing multi-agent LLM systems, grounded in the observation that the external organization of agents (folders, identity files, isolation boundaries) can be aligned with the internal organization of knowledge in LLMs (entity subspaces, orthogonal representations, bottleneck filtering). The architecture defines two agent types (leaf and non-leaf), four isolated infrastructure roles (attention, verification, knowledge, communication), and a recursive structure with no fixed depth. Independent evidence from recent work on persistent cognitive agents (arXiv:2604.12016) confirms the core mechanism: identity documents induce attractor-like structure in LLM activation space.

1. The mistake we made

We designed the system around agents: create agent, write CLAUDE.md, register in agents.md, open a window, dispatch tasks. Because we know how agents work, we made the interface about agents.

But even the designer — the person who built the system — doesn't want to manage agents. They want to say "I have a Kaggle competition" and start working.

The curse of knowledge: Because we understand the implementation, we designed the interface around the implementation. The user sees agents. But the user thinks in tasks.

Tasks are the only concept the user needs. Everything else is the system's problem.

25. The #1 characteristic: clean context

Before identity, before communication, before everything else: clean context.

When an LLM opens a folder, it reads the files. Those files become its context. The context IS its mind. The folder determines what the agent thinks about.

Clean folder → clean context → focused agent.
Mixed folder → mixed context → confused agent.

The folder doesn't organize files. The folder organizes the agent's THINKING.

This isn't a design choice. It's aligned with how the model works. From our research:

Model internals: Each entity → own subspace (cos 0.92 stable) L14 bottleneck → filters noise, keeps structure Clean input → clean representation → correct output Agent architecture: Each agent → own folder (isolated) CLAUDE.md → defines scope, filters irrelevant content Clean folder → clean context → focused work Same principle. The folder structure maps to the model's internal structure. Clean subspaces = clean folders.

The model reads "auto-build/" and activates the right knowledge. It reads "math-modeling/" and activates different knowledge. The folder name IS the entity label. CLAUDE.md IS the entity definition. The files ARE the subspace.

This is why isolation matters: not for file management, but for cognitive hygiene. A mixed folder is a noisy subspace — the model can't think straight.

27. The nine characteristics

1. Self-aware. The agent knows what it is. CLAUDE.md tells it. Any LLM opens the folder, reads CLAUDE.md, and becomes the agent. The identity is in the file, not in the model.
2. Scoped. The agent knows its boundary. "I handle X. I do NOT handle Y." This prevents scope creep. When a task doesn't fit, the agent says so — the brain routes it elsewhere.
3. Communicable. Standard I/O. TASK.md goes in. REPORT.md comes out. Any agent can send a task to any other agent. The format is universal. No custom APIs between agents.
4. Isolated. Own folder. Own data. Own tasks. Agent A can't accidentally read agent B's files. The folder boundary IS the isolation. No shared state except through explicit file exchange.
5. Stateful. Everything is on disk. The agent can be killed and restarted. A new LLM session opens the folder, reads the files, and picks up where the last session left off. Memory is files, not context windows.
6. Observable. You can check the agent's progress without interrupting it. Task status, REPORT.md, logs — all readable from outside. The brain reads these to report status to the user.
7. Recoverable. If the agent crashes, nothing is lost. State is in files. Open a new terminal, point it at the same folder, it resumes. No "session state" that vanishes when the window closes.
8. Composable. Agents can chain. Agent A's REPORT.md becomes agent B's TASK.md. Because the interface is standard (files), agents don't need to know about each other. The brain composes them.
9. Growable. An agent starts with CLAUDE.md + one task. It gains structure only when needed — specs, tools, plan-verify, sub-agents. It's never over-designed at birth. It grows from use.

31. Clean check: the brain's hygiene loop

Context gets dirty over time. Files drift into the wrong agent. Topics mix. The brain needs to catch this automatically.

Brain clean check (runs when idle): 1. Read agents.md → list all agents 2. For each agent: a. Read CLAUDE.md → understand scope b. Scan folder contents c. For each file/subfolder: does this belong to this scope? 3. If mismatch found: a. Identify which agent the file SHOULD belong to b. Report: "{file} in {agent} → should be in {correct-agent}" c. Auto-fix or ask user 4. Check for agent-less content: a. Files in agents/ root that aren't an agent folder b. Suggest: create new agent or move to existing one

The brain is the ONLY one who can do this. Individual agents can't judge their own files (bias). The brain sees all agents, knows all scopes, and can route correctly.

This is the immune system. The clean check prevents context contamination the same way an immune system prevents infection. It runs continuously, detects foreign bodies (misplaced files), and removes them.

Without it, entropy wins. Files accumulate. Contexts get noisy. Agents get confused. The clean check is what keeps the system healthy over time.
Example clean check output: ✓ brain/ 3 files, all routing-related ✓ auto-build/ clean — loop docs + 2 task folders ✗ math-modeling/ ISSUE: math-rendering/ has 80+ HTML files covering 15+ different topics. Suggest: move topic-specific files to their own agents or archive. ✓ algorithm-optimization/ clean — plan-verify + working ✓ resume-writer/ clean ✗ text-to-sql/ ISSUE: archive/ contains old versions. Suggest: move to text-to-sql.portal_bak or delete if backed up.

The clean check doesn't need to be perfect. It just needs to catch the obvious contamination — files that clearly belong to a different scope. Over time, it keeps the system clean enough for focused work.

31. The brain's loop

The brain is not a batch processor. It is a loop. It listens, routes, watches, cleans, and listens again. This is the operational cycle — not a design principle, but the actual sequence of actions.

1. LISTEN — what did the user say? not the words. the need. 2. PARSE — is the intent clear enough to match? 3. CLARIFY — not clear? ask the user. converge on intent. 4. MATCH — clear → which agent handles this? → found → LAUNCH → not found → CREATE → LAUNCH 5. LAUNCH — open the agent's window. user interacts directly. 6. WAIT — user is with the agent. brain idles. 7. RETURN — user comes back. read REPORT.md. update tasks.md. 8. CLEAN — scan all folders. move misplaced files. fix scope. 9. LISTEN AGAIN

Step 3 is critical: the brain is not a one-shot resolver. When the user says "I need to do something with data," the brain doesn't guess. It asks: "What kind of data work? Analysis, pipeline, training?" One or two questions is usually enough. The brain converges on the intent through conversation, then matches.

The brain never dead-ends. Unclear → clarify. Clear but no match → create. Clear and match → launch. Every path leads to an open window.

The loop has a deep property: it directs attention, never does the work. If the brain catches itself writing code, analyzing data, or drafting text — it has broken the loop. That work belongs to an agent. The brain's only output is: an open window pointed at the right agent.

32. Context switching

The hardest thing the brain does is switch. Not because it's complex — but because it must be lossless.

SWITCH protocol: User: "Switch to rogii" Brain: 1. SAVE current context • Current agent writes state to its task folder • Any uncommitted observations → notes in REPORT.md • Current task status updated in tasks.md 2. LOAD target context • Find: tasks.md → rogii → agent: auto-build • Read: auto-build/CLAUDE.md (become this agent's brain) • Read: auto-build/tasks/rogii/TASK.md (the contract) • Read: auto-build/tasks/rogii/REPORT.md (where we are) 3. RESUME • The files ARE the state. No "session" to restore. • The brain reads the files and knows exactly where the agent left off.

This is why stateful = files, not memory. A context window dies when the terminal closes. A file doesn't. The switch works because there is nothing to transfer — everything is already on disk.

Context switching cost in this system: zero.
In a traditional system, switching context means serializing state, transferring it, deserializing it. Here, the state was never in memory. It was always on disk. "Switching" just means: read a different folder.

33. Error modes

Three things go wrong. Only three.

1. Misroute
The brain sends a task to the wrong agent. The agent either fails (doesn't know how) or produces the wrong output (knows how, but shouldn't).

Detection: REPORT.md doesn't match TASK.md expectations. Or the agent says "this isn't my scope."
Recovery: Move TASK.md to the correct agent. Update tasks.md. The work already done may or may not transfer — that's fine.
2. Scope creep
An agent starts handling things outside its CLAUDE.md. Files appear in the folder that don't match the scope. The clean check catches this, but between checks, contamination can spread.

Detection: Clean check finds mismatched files. Or the brain notices the agent talking about topics outside its scope.
Recovery: Move files. Tighten CLAUDE.md. If the agent's domain legitimately grew, update the scope — don't fight organic growth, but name it.
3. Stale task
A task sits in "active" status but no one is working on it. The agent crashed, the user forgot, or the task is blocked on something external.

Detection: tasks.md shows "active" but REPORT.md hasn't changed. Or the user asks "what's going on?" and the brain has nothing to report.
Recovery: Ping the agent. If no response, check the task folder for clues. If blocked, mark as "blocked" with reason. If abandoned, mark as "paused."

Notice: all three errors are detectable from files. No logs, no monitoring, no health checks. Read the folder. If it looks wrong, it is wrong.

34. The naming system

Names in this system are not labels. They are addresses.

Unix: /usr/bin/grep ← path IS the address DNS: api.example.com ← name IS the address Plan 9: /net/tcp/80/data ← path IS the protocol Ours: agents/auto-build/tasks/rogii/TASK.md agents/ ← namespace root auto-build/ ← which process (agent) tasks/ ← what kind of thing (structure) rogii/ ← which instance (task) TASK.md ← what to read (contract)

Every level of the path answers a question. There is no ambiguity. There is no lookup table. The path IS the resolution.

This has a consequence most systems miss: naming errors are routing errors. If the folder is named wrong, the brain will misroute tasks to it. If TASK.md is missing, the agent won't know what to do. The filesystem is the API — and the filename is the endpoint. Naming isn't cosmetic. It's structural.

Naming rules:
• Agent names: kebab-case, describes the domain. auto-build, not builder. resume-writer, not resumes.
• Task names: kebab-case, describes the specific instance. rogii, not task-1. resume-google, not resume.
• File names: UPPER.md for contracts (TASK.md, REPORT.md, CLAUDE.md). lower.md for everything else.

If you can't name it in two words, you don't understand the scope yet.

35. Plan 9 and the filesystem-as-OS

In 1992, Rob Pike and Ken Thompson built Plan 9 at Bell Labs. Their insight: Unix said "everything is a file" but didn't mean it. Devices were files, but networks weren't. Processes had /proc, but couldn't be composed through the filesystem. Plan 9 made it literal.

Plan 9: /net/tcp/clone → open this file to create a TCP connection /proc/42/status → read this file to see process state /mnt/remote/ → another machine's filesystem, mounted locally Ours: agents/auto-build/CLAUDE.md → read this file to become the agent agents/auto-build/tasks/rogii/ → open this folder to work on the task tasks.md → read this file to see all task states

The parallel is not metaphorical. It is structural. Both systems use the filesystem as the sole coordination mechanism. No message queues. No service registries. No configuration files that point to other configuration files. The path IS the address. The file IS the state. The folder IS the isolation boundary.

Plan 9 failed commercially because it was too radical for its time. But the idea was right: if you make the filesystem expressive enough, you don't need anything else. Our system proves it for a different domain: agent coordination.

36. Why not a database? Why not an API?

The obvious engineering question: why not use a proper coordination layer?

ApproachWhat it givesWhat it costs
DatabaseQueries, indices, ACIDSchema, migrations, connection pooling, ORM, deployment
Message queueAsync, ordering, replayBroker, serialization, dead letter queues, monitoring
REST APIStandard interface, toolingServer, auth, versioning, documentation, uptime
FilesystemNaming, isolation, persistenceNothing. It already exists.

The cost column is the answer. Every coordination layer adds infrastructure that must be built, maintained, and debugged. The filesystem is free. It's already there. It already does naming, persistence, isolation, and hierarchy.

The tradeoff: we lose queries (can't ask "show me all active tasks across all agents" without scanning folders) and we lose atomicity (two agents could write to the same file). In practice, neither matters:

• We don't need complex queries — tasks.md IS the query result, maintained by the brain.
• We don't have concurrent writes — one agent per folder, one brain routing. No conflicts by design.

The filesystem is not a compromise. It is the correct abstraction for this problem. Agent coordination is a naming + isolation + persistence problem. The filesystem solves all three natively.

37. The two clocks

The system runs on two clocks. Understanding them prevents most operational confusion.

Clock 1: User time The user arrives with a task. Minutes to hours later, they want results. The user thinks in: tasks, status, deliverables. Interface: tasks.md. Clock 2: Agent time The agent works in iterations. Each iteration: read TASK.md, do work, update REPORT.md. An iteration takes seconds to minutes. The agent thinks in: steps, experiments, outputs. Interface: REPORT.md.

The brain bridges the two clocks. When the user asks "what's going on?", the brain translates agent-time progress into user-time status. "Iteration 12, RMSE 4.1" is agent-speak. "Getting closer, accuracy improved 50% from start" is user-speak. The brain translates.

The mismatch between the two clocks is where frustration lives. The user wants to know if it's done. The agent wants to know what to try next. The brain must satisfy both without confusing either.

Part III: Implementation

40. Building the brain

Theory is done. Now we build. The brain is not a program — it's a set of files that make an LLM behave as a router. "Building" means: writing the right files so that any LLM session that opens this folder becomes the brain.

The brain is four files: brain/ CLAUDE.md ← identity + protocol (WHO I am, HOW I route) agents.md ← routing table (WHERE to send tasks) tasks.md ← task registry (WHAT the user sees) loop_prompt.md ← operational loop (the cycle I run)

That's it. No code. No framework. No deployment. Write four files. Open a terminal. Point Claude at the folder. The brain boots.

41. agents.md: the routing table

This is the brain's process table. Every active agent in the system, with enough information to route.

| id | name | domain | status | |----|------|--------|--------| | 01 | math-modeling | LLM internals research | active | | 02 | auto-build | build systems from eval sets | active | | ... Routing algorithm: 1. User says X 2. Brain reads agents.md 3. For each row: does X match this domain? 4. Best match → route 5. No match → CREATE new agent

The routing is semantic, not keyword-based. "I have a Kaggle competition" matches auto-build not because of keywords, but because the LLM understands that building a competition solution IS "building systems from eval sets." The domain description is a prompt, not a filter.

Design decision: agents.md is flat. No hierarchy. No categories. The brain scans linearly. With 15 agents, this is instant. With 100, it might need grouping. We'll cross that bridge when we feel the pain — not before.

42. tasks.md: the user interface

This is the ONLY file the user needs to understand. It shows what they asked for and where it stands.

| task | status | agent | description | |------|--------|-------|-------------| | entity-research | paused | math-modeling | 144 experiments, paper draft v4 | | paper | active | math-modeling | "The Geometry of Knowing and Saying" | | banking77 | done | auto-build | 0% → 82% held-out from empty | | rogii | new | auto-build | Kaggle $50K geology prediction | Status values: new — created, not started active — agent is working on it paused — stopped, can resume blocked — waiting on something external done — complete, deliverable ready

The agent column is invisible to the user in spirit — they don't care which agent handles it. But it's visible in practice because the user IS the designer right now. Later, it could be hidden.

43. CLAUDE.md: the brain's identity

This file makes any LLM session become the brain. It must contain:

1. IDENTITY — "I am the brain. I route tasks to agents." 2. PROTOCOL — the loop: LISTEN → PARSE → MATCH → DISPATCH 3. BOUNDARIES — "I do NOT do the work. I route." 4. FILES — which files I read and write 5. AUTO-CREATE — how to create a new agent 6. CLEAN CHECK — how to audit agent contexts

The CLAUDE.md is short. Under 50 lines. The LLM doesn't need a textbook — it needs a role definition. The loop_prompt.md adds depth for when the brain needs to reflect on its own process.

44. The dispatch protocol

How the brain actually sends work to an agent. This is the IPC mechanism.

LAUNCH(task_name, agent_name, user_request): 1. Resolve path: agents/{agent_name}/ 2. If new task: a. Create: agents/{agent_name}/tasks/{task_name}/ b. Write TASK.md (what, context, deliverable) c. Update tasks.md: add row 3. Open the agent's window: a. New Claude session pointed at agents/{agent_name}/ b. The agent reads its own CLAUDE.md, becomes itself c. The agent runs its own ENTRY CHECK on the task d. The agent reads tasks/{task_name}/TASK.md, starts working 4. User talks directly to the agent. The brain is no longer in the conversation. The user and the agent work together. The brain waits at its home window.

The brain launches at the agent level. It checks: does this agent exist? Does it have a CLAUDE.md? Is it registered? That's the brain's scope. The brain doesn't look inside the task folder — that's the agent's business.

The entry check belongs to the agent, not the brain. When the agent starts, it checks its own task context before working:

Agent entry check (runs on startup): 1. Read CLAUDE.md — who am I? 2. Scan task folder — is the context clean? • Stale files? Leftover from previous attempt? • TASK.md current? Or outdated from a different session? • REPORT.md from a finished task still sitting as "active"? • Files that don't belong to this task? 3. If dirty → clean first, then work. 4. If clean → read TASK.md, start working.

This is the right separation. The brain checks agents (system level). The agent checks tasks (task level). Each level is responsible for its own cleanliness. The brain doesn't micromanage task folders. The agent doesn't worry about other agents.

Brain scope: which agent? does it exist? launch it.
Agent scope: which task? is it clean? work on it.

The L14 bottleneck is at the AGENT level, not the brain level. The agent filters its own noise before computation begins. The brain just activates the right agent — what happens inside is the agent's responsibility.

When the user is done, they return to the brain window. The brain reads REPORT.md to see what happened. The cycle continues.

45. The status protocol

When the user asks "what's going on?", the brain does a sweep.

STATUS(): 1. Read tasks.md → list of (task, status, agent) 2. For each active task: a. Read agents/{agent}/tasks/{task}/REPORT.md b. Extract last update (first line or last section) 3. Present to user: task-name status last update ───────── ────── ─────────── rogii active iter 12, RMSE 4.1 paper active draft v5, methods section done banking77 done 82% held-out accuracy If no REPORT.md exists: status is "dispatched, no report yet." If REPORT.md says DONE: update tasks.md status to done.

The status sweep is the brain's read-only operation. It never modifies agent files during status. It only updates tasks.md if it discovers a task is done.

46. The create protocol

When the brain can't match a task to any agent, it creates one. This is fork().

CREATE(domain_name, first_task, user_request): 1. Pick name: kebab-case, 2-3 words, describes the domain "I need to analyze churn data" → data-analysis "Write a comic about my cat" → comic-agent "Help me study for GRE" → test-prep 2. Create folder structure: mkdir agents/{name} mkdir agents/{name}/tasks mkdir agents/{name}/tasks/{first_task} 3. Write CLAUDE.md (one paragraph): "# {name} I {verb} {domain}. I read TASK.md for each task. I write results to REPORT.md." 4. Register in agents.md: | {next_id} | {name} | {domain description} | active | 5. Write TASK.md for the first task (normal DISPATCH) 6. Report: "Created {name} agent. First task: {first_task}." Total cost: 3 folders, 3 files. Under 10 lines of content. Total time: instant. The agent exists.

The key insight: creating an agent is cheap. Cheaper than deliberating about whether to create one. If in doubt, create. If it turns out to be wrong, the clean check will merge or remove it later. Agents are cattle, not pets.

47. Multi-agent dispatch

Sometimes one user request needs multiple agents.

User: "I need a resume for Google and also check how the Kaggle competition is going." Brain parses TWO intents: 1. "resume for Google" → resume-writer 2. "check Kaggle status" → auto-build (status check) Actions: 1. DISPATCH("resume-google", "resume-writer", ...) 2. STATUS() for rogii task 3. Report both results to user

The brain decomposes before routing. One sentence can contain multiple tasks. The parse step must catch this. If it doesn't, the user will say "you forgot about the Kaggle thing" — and the brain will learn.

49. What the brain IS and is NOT

The brain is not a router. A router just forwards packets. The brain understands intent, decides where attention goes, launches agent sessions, manages switching, and maintains the system. That's a brain.

The brain is a brain.
A human brain doesn't proxy between your eyes and your hands. It doesn't relay messages. It directs attention. It decides what to focus on. It launches motor programs. It switches between tasks. It never does the specialized work — but without it, nothing coordinates.

The name was right all along. The description was wrong.
The brain is NOT a proxy.
It doesn't sit between the user and the agent, relaying messages. That wastes context, loses information, and makes the brain a bottleneck. The brain opens the window. The user talks directly to the agent.
The brain is NOT a router.
A router forwards packets without understanding them. The brain understands the user's intent, matches it to a domain, and creates agents that don't exist yet. Routers don't create endpoints.
The brain is NOT an orchestrator.
An orchestrator controls execution: start, stop, monitor, retry. The brain launches and lets go. The agent runs its own execution with the user directly.
The brain is NOT a planner.
A planner decomposes goals into sub-steps. That's plan-verify's job. The brain decides WHERE attention goes, not HOW the work gets done.
What the brain does: • Understands — parses user intent into tasks • Decides — matches tasks to agents • Launches — opens agent windows for direct interaction • Creates — spawns new agents when no match exists • Switches — saves context, opens different agent window • Maintains — clean check, system hygiene, routing table What the brain doesn't do: • Work — never writes code, analyzes data, drafts text • Proxy — never relays between user and agent • Plan — never decomposes tasks into sub-steps • Judge — never evaluates agent output quality

Part IV: The Leaf Agent

51. The leaf agent's goal: act well

The brain routes. The leaf acts. That's the entire system in two words.

But "act" is easy. Any LLM can act — generate code, draft text, run experiments. The problem is acting well. An LLM that acts without feedback will:

• Write code that looks correct but fails on edge cases • Draft a resume that sounds impressive but misses the JD keywords • Train a model for 50 iterations past the point of diminishing returns • Solve the wrong problem confidently

The leaf agent can act. But it cannot see its own action from outside. It's inside the execution. It sees what it intended, not what it produced. Like a writer who rereads their draft and sees the essay they meant to write, not the one they actually wrote.

This is not a bug. It's a structural property of generation. The same process that produces output cannot simultaneously evaluate that output, because evaluation requires a different viewpoint — a context that doesn't carry the momentum of generation.

52. The optimization decomposition

Every optimization system has two components:

Generator — produces candidates Evaluator — scores candidates Loop — generator produces → evaluator scores → generator adjusts Gradient descent: forward pass (generate) + loss function (evaluate) Evolution: mutation (generate) + fitness function (evaluate) Science: hypothesis (generate) + experiment (evaluate) Writing: draft (generate) + editing (evaluate)

You cannot optimize with only a generator. You cannot optimize with only an evaluator. And critically: they must be separate. A generator that evaluates itself is just a generator with extra tokens. The evaluation must come from a different context, a different session, a different viewpoint.

Plan-verify + working IS this decomposition:

Working = generator. Its job is to act. Produce output. Write code. Draft text. Run the experiment. Don't judge. Don't second-guess. Act.

Plan-verify = evaluator. Its job is to see. Read the output. Compare to the goal. Is this good enough? If not, what's wrong? Send feedback. Don't do the work. Judge the work.

The loop = optimization. Working acts → plan-verify evaluates → working acts again with feedback → repeat until plan-verify says done.

This is why the split works: it maps to the fundamental structure of optimization. Not because "management is good" or "verification catches bugs" — but because you cannot converge without a loss function, and the loss function must be external to the generator.

53. Why two sessions, not one

Why can't a single LLM session both act and evaluate?

It can try. Every LLM does this internally — "let me check my work." But there's a structural problem: context momentum.

Session that just WROTE the code: • Remembers why each decision was made • Sees the intent behind each line • Carries the reasoning that led to this solution • Evaluates: "yes, this is correct" (it would — it just wrote it) Fresh session that READS the code: • Sees only the output, not the intent • Reads what's written, not what was meant • Has no attachment to the approach • Evaluates: "line 42 has a bug, and the whole approach misses the constraint in TASK.md paragraph 3"

The first session can't see its own blind spots because the blind spots are part of its context. The second session has no blind spots about this code — it has a fresh context. This is why code review works. This is why editors exist. This is why science requires independent replication.

Plan-verify is a fresh session. It reads TASK.md (what was asked) and REPORT.md (what was done). It has no memory of the struggle, the tradeoffs, the "I tried X but it didn't work so I did Y." It sees the output cold. That's exactly what evaluation requires.

54. The leaf agent's structure

A leaf agent that needs to act well has exactly this structure:

{agent}/ CLAUDE.md ← identity: what domain I handle plan-verify/ CLAUDE.md ← "I plan tasks and verify results" working/ CLAUDE.md ← "I execute. I act. I produce artifacts." tasks/ {task-name}/ TASK.md ← contract (from brain or plan-verify) REPORT.md ← output (from working, read by plan-verify) The flow: 1. Brain dispatches TASK.md to the agent 2. Plan-verify reads TASK.md, writes a specific action plan 3. Working reads the plan, ACTS, writes REPORT.md 4. Plan-verify reads REPORT.md, compares to TASK.md • Good enough → done • Not good enough → writes feedback, working acts again 5. When plan-verify says done, brain reads the final REPORT.md

Working never decides "am I done?" Plan-verify never does the work. The separation is absolute.

55. When to split, when not to

Not every leaf agent needs plan-verify + working. The split is needed when the action is complex enough that self-evaluation fails.

Don't split (P0 is enough): • The action is simple and verifiable by inspection • "Convert this CSV to JSON" — either it works or it doesn't • "Summarize this document" — one-shot, no iteration needed • The cost of a bad output is low Split (P0 + P1 needed): • The action requires iteration to converge • "Build a model that gets 80% accuracy" — needs feedback loop • "Write a resume that matches this JD" — needs draft → review cycles • "Optimize this SQL query" — needs measurement → adjustment • The cost of a bad output is high

The heuristic: if a human would want to review the output before shipping it, the agent needs plan-verify. If a human would trust the output sight-unseen, P0 is enough.

57. Why this is not hierarchy

It looks like a hierarchy: brain → plan-verify → working. Three levels. Top-down control. But it's not.

A hierarchy means: the top decides, the bottom obeys. The top is smarter. The bottom is dumber. Information flows up, commands flow down.

This system is different: each level does something the others structurally cannot.

Brain can't act — it sees all agents but no task details. — it has breadth but no depth. Plan-verify can't act — it sees the goal and the output but wasn't inside the execution. — it has judgment but no generation momentum. Working can't judge — it was inside the execution. it sees intent, not output. — it has generation momentum but no distance. Working can't route — it sees only its own folder. it doesn't know other agents exist.

It's not hierarchy. It's separation of concerns along cognitive boundaries. Each role operates in a context that makes it good at exactly one thing and structurally incapable of the others. That's not management — it's architecture.

Operating system parallel: Scheduler (brain) — decides WHICH process runs Debugger (plan-verify) — inspects process output Process (working) — runs the computation The scheduler can't debug. The debugger can't compute. The process can't schedule. Not because of permissions — because each operates on different information.

The leaf agent's goal is to act well.
Acting is easy. Acting well requires a feedback loop.
The feedback loop requires separation: generator + evaluator.
Working generates. Plan-verify evaluates. The loop converges.
This is not management. This is optimization.

Part V: The Brain Is a Brain

58. The wrong metaphor

We called it a router. A switchboard. A receptionist. All wrong.

A router forwards packets without understanding them. A switchboard connects cables without knowing who's talking. A receptionist sends you to a room and forgets you exist.

The brain does something none of these do: it understands intent, creates new agents that didn't exist, and maintains the health of the entire system. Routers don't create endpoints. Switchboards don't redesign the wiring. Receptionists don't scan every room for contamination.

59. The right metaphor

A human brain.

Human brain: • Receives sensory input → LISTEN • Interprets meaning → PARSE • Asks for more info if unclear → CLARIFY • Selects motor program → MATCH • Creates new neural pathways → CREATE • Launches the motor program → LAUNCH • Attention goes to the limb → user talks to agent • Monitors via feedback → WATCH (reads REPORT.md) • Housekeeping while idle → CLEAN (like sleep consolidation)

The brain doesn't move your hand. It doesn't proxy between your eyes and your fingers. It directs attention to the right motor program, and the motor program executes with direct sensory feedback. Your hand feels the object. Your hand adjusts grip. The brain doesn't micromanage — it launched the right program and let go.

When you want to switch from typing to reaching for a cup, you don't "save typing state and load cup-reaching state." Your brain shifts attention. The motor programs are already there, already capable. The brain just points.

The brain is the attention system.
It decides WHAT to focus on. The agents are the motor programs — they know HOW to do their thing. The user is the sensory input — they provide intent. The brain connects intent to capability.

This is why the user talks directly to agents. You don't think "brain, tell my hand to grip harder." You think "grip harder" and the motor program does it, with direct feedback from your fingers. The brain enabled the connection. It doesn't stay in the loop.

The brain is the home screen. You come to it to navigate. Then you enter an app (agent). The app has the full experience. When you're done, back to home.

61. What the brain does when idle

While the user is talking to an agent, the brain is idle. But "idle" doesn't mean "off." The human brain does critical work during idle states — memory consolidation, garbage collection, system maintenance. So does ours.

Brain idle tasks: 1. CLEAN CHECK Scan all agent folders for context contamination. Files that don't match scope → flag or move. Agents not in agents.md → register or investigate. 2. STATUS SWEEP Read all REPORT.md files. Update tasks.md with current status. Mark completed tasks as done. 3. HEALTH CHECK Any agent folder missing CLAUDE.md? → write one. Any task folder missing TASK.md? → flag. Any stale "active" tasks? → mark as paused. 4. GROWTH CHECK Any agent handling too many domains? → suggest split. Any two agents overlapping? → suggest merge. Any agent's CLAUDE.md outdated? → suggest rewrite.

This is the immune system + the janitor + the gardener. It runs in the background. The user never sees it. But without it, entropy wins and the system degrades.

Part VI: Why It Works — The Theoretical Foundation

63. The LLM already knows

Here's what this system does NOT do: teach the LLM domain knowledge.

The LLM already knows how to write resumes. It knows how to build ML models. It knows how to optimize SQL. It knows how to write papers. All of this knowledge is already inside the model, distributed across its parameters.

The system doesn't add knowledge. It activates it.

CLAUDE.md doesn't teach. It activates.
Writing "I am a resume writer" doesn't teach the LLM about resumes. It focuses the LLM's existing knowledge on resume-writing. It suppresses everything irrelevant. It creates a clean activation context.

The folder doesn't add information. It removes noise. And removing noise IS the job — because the model's failure mode is not "doesn't know enough." It's "knows too much and can't focus."

This is why the system is so cheap to build. You don't encode domain expertise. You don't write knowledge bases. You don't train specialists. You organize pointers — folder names, CLAUDE.md files, TASK.md contracts — that point the LLM's existing knowledge at the right problem.

64. Entity subspaces: the internal evidence

We know this is true because we've measured it inside the model.

From 144 experiments on LLM internals ("The Geometry of Knowing and Saying", math-modeling agent):

Each entity occupies its own stable subspace.
• Effective rank: r_eff = 5–9 dimensions
• Cosine stability: 0.92 across different contexts
• Angles between entity subspaces: 77–84° (nearly orthogonal)
• Countries distinguishable at r_eff = 5.8

What this means:
When the model processes "France", a specific 5–9 dimensional subspace activates. When it processes "Japan", a different subspace activates, nearly orthogonal to the first. The subspaces are stable — regardless of whether the context says "the capital of France" or "French cuisine" or "France in WWII", the same geometric region lights up.

The subspace IS the knowledge. Not a pointer to knowledge. Not an index. The subspace itself is the computational space where the model does its thinking about that entity.

The model doesn't store "France" as a fact. It stores France as a geometric region — a low-rank subspace that activates when France is relevant and stays silent when it's not.

65. The L14 bottleneck: the internal noise filter

The model has its own version of "clean context":

Layer 1–13: information accumulates. Multiple entities active. Layer 14: bottleneck. Noise filtered. Only relevant subspace survives. Layer 15+: clean representation → correct output. Causal evidence: Intervene at all layers: 20–46% performance drop Intervene at random layers: ~0% drop Early/mid layers carry the signal. The bottleneck cleans it.

The model has a built-in isolation mechanism. It doesn't need external help to separate entities — it does it internally through the bottleneck layer. Noise in, clean signal out. Mixed context in, focused representation out.

The agent architecture mirrors this exactly:

Model internals: Agent architecture: ───────────────── ───────────────────── Entity subspace (r=5-9) ↔ Agent folder (isolated) cos 0.92 stability ↔ CLAUDE.md (consistent identity) 77-84° between entities ↔ Separate folders (no overlap) L14 bottleneck (filter) ↔ Folder boundary (noise wall) Clean representation ↔ Clean context Correct output ↔ Focused work

66. The architecture mirrors the model

This is not a metaphor. It is a structural correspondence.

Inside the model:
Knowledge lives in subspaces. Each entity has its own geometric region. The regions are nearly orthogonal — they don't interfere. A bottleneck layer filters noise. Clean subspace → correct computation.

Outside the model (our system):
Knowledge lives in folders. Each agent has its own directory. The directories don't share files — they don't interfere. CLAUDE.md scopes the context. Clean folder → focused agent.

The folder IS the external subspace.
CLAUDE.md IS the external entity definition.
The folder boundary IS the external bottleneck.
The brain IS the external attention mechanism.

The system works because it's aligned with how the model already organizes knowledge internally. We're not imposing structure on the model — we're providing external structure that matches its internal structure. The model meets us halfway.

67. Diagnosis, not teaching

The brain's job becomes clear in this light. The brain doesn't teach agents. It doesn't transfer knowledge. It diagnoses the user's intent and activates the right subspace by pointing the model at the right folder.

User: "I need to write a resume for Google." The system is an attention management system, not a knowledge system. The knowledge is already there. The system manages which knowledge is active.

This is, again, exactly what a human brain does. Your visual cortex already knows how to process images. Your motor cortex already knows how to grip. Your language centers already know grammar. The brain doesn't teach any of them. It directs attention to the right system at the right time.

68. Why the folder name matters so much

In section 34 we said: naming errors are routing errors. Now we can say why at a deeper level.

The folder name is the entity label. When the model reads "auto-build/", it activates the subspace associated with building, automation, iteration, eval sets. When it reads "resume-writer/", it activates a completely different subspace — formatting, keywords, professional language, PDF generation.

Suppresses: nothing Result: unfocused, confused agent

A bad folder name is like a corrupted entity label — it activates the wrong subspace, or no coherent subspace at all. The model has the knowledge but can't find it because the activation signal is wrong.

This is why naming is structural, not cosmetic. The name IS the activation function.

69. The double sparsity principle

From the entity subspace research: knowledge in LLMs is doubly sparse.

Sparsity 1: Token sparsity Not all tokens matter. The entity information concentrates at specific positions (typically the last token of the entity mention). Sparsity 2: Dimension sparsity Not all dimensions matter. The entity occupies a low-rank subspace (r=5-9) out of thousands of available dimensions. Entity = sparse patch in token × dimension space.

The agent architecture has the same double sparsity:

Sparsity 1: File sparsity Not all files matter. CLAUDE.md and TASK.md carry the signal. The rest is work product. Sparsity 2: Folder sparsity Not all folders matter. Only the current agent's folder is active. The other 13 agents are silent. Agent = sparse patch in file × folder space.

Double sparsity is why the system scales. With 14 agents and hundreds of files, only one folder with a few key files is active at any time. The rest is suppressed. Just like the model: thousands of dimensions, but only 5–9 carry the signal for any given entity.

Part VII: What We Got Wrong

71. The corrections ARE the design

This document was not written in one pass. It was written across a single session, and the understanding evolved as we wrote. The corrections are not embarrassments — they are the most valuable content. Each correction reveals a misconception that would have broken the system.

72. Wrong: one window

What we said (section 4, first draft):
"One window. The user just talks. The system grows."

What was wrong:
One window means the brain proxies every conversation. The user talks to the brain. The brain talks to the agent. The agent talks to the brain. The brain talks to the user. Every message passes through the brain. The brain becomes a bottleneck, a translator, a lossy channel.
The correction:
The brain opens agent windows. The user talks directly to the agent. The brain is the home screen, not the conversation partner. Navigate at the brain. Work at the agent. This is natural — you don't talk to your brain, you talk through it.

The correction came from a simple observation: "the natural is not people interact with one window, brain open the agent window, let user interact, it's nature." The user saw what we missed — the proxy model is unnatural because humans don't proxy their own thoughts.

73. Wrong: router / switchboard

What we said (sections 12, 31, loop_prompt.md, first drafts):
"The brain is a switchboard." "The brain is a router." "Like a telephone operator — Number please? Plugs the cable."

What was wrong:
A router forwards packets without understanding them. A switchboard connects cables without knowing who's talking. But the brain understands intent. It creates agents that don't exist. It maintains system health. Routers don't create endpoints. Switchboards don't redesign the wiring.
The correction:
The brain is a brain. It directs attention. It launches motor programs. It maintains the organism. The name was right from the start — the description was wrong. A brain doesn't proxy between your eyes and your hands. It activates the right motor program and lets it run with direct feedback.

The too-modest metaphor caused real design errors. If the brain is "just a router," then dispatch means "forward a message." But if the brain is a brain, then dispatch means "launch a window, direct attention, let go." The metaphor shapes the mechanism.

74. Wrong: priorities for leaf agents

What we almost wrote:
Five priorities for leaf agents: start immediately, produce artifacts, report, stop when done, fail loudly.

What was wrong:
We were solving a problem that doesn't exist. The plan-verify + working split already makes all five "priorities" structurally impossible to violate. We were adding instructions where architecture was needed.
The correction:
The leaf agent has ONE goal: act. To make it act well, you add plan-verify + working — a generator and an evaluator. The evaluator is the loss function. You can't optimize without a loss function, and the loss function must be external to the generator. This is not management. It is optimization.

The deeper lesson: don't solve with instructions what you can solve with architecture. Instructions can be ignored. Architecture can't. If you need the agent to stop when it's done, don't tell it to stop — give it a verifier that decides when it's done.

75. Wrong: the system teaches knowledge

What we implicitly assumed:
CLAUDE.md defines what the agent knows. The folder structure organizes knowledge. The system is a knowledge management system.

What was wrong:
The LLM already knows everything it needs to know about resumes, ML, SQL, and every other domain. CLAUDE.md doesn't teach. It activates. The folder doesn't store knowledge. It removes noise.
The correction:
The system is an attention management system, not a knowledge system. The knowledge is pre-existing in the model's parameters, organized in low-rank subspaces (r=5-9, cos 0.92). The folder name activates the right subspace. CLAUDE.md tightens the scope. The system manages which knowledge is active, not what the knowledge is.

This correction came from connecting the agent architecture to the entity subspace research. The same mechanism that organizes entities inside the model (subspaces, orthogonality, bottleneck filtering) is what the folder structure does externally. The system doesn't fight the model. It aligns with it.

76. The pattern of corrections

Every correction follows the same pattern:

Wrong: we overestimated what the system needs to do. Right: the system does less than we thought. One window → brain just launches, doesn't proxy Router → brain just directs, doesn't forward Five priorities → architecture provides them, not instructions Knowledge system → knowledge already exists, system just activates

The system got simpler with every correction. Not more complex. Every time we thought we needed to add something, the answer was: the model already does that. Get out of the way.

The best system design is the one that removes the most.

We didn't add routing — we removed the proxy.
We didn't add priorities — we removed them and used architecture.
We didn't add knowledge — we removed noise so existing knowledge could focus.
We didn't design the system — we removed our misconceptions about what it needed to be.

90. Three levels, each checks its own

Brain checks at the agent level:
• Does this agent exist? Does it have a CLAUDE.md?
• Is it registered in agents.md?
• Clean check: files match scope? agents overlap?
• Match, create, launch.

Plan-verify checks at the task level + output level:
• Entry check: Is the task folder clean? TASK.md current? Stale files?
• Plan: Read TASK.md, decompose into steps, dispatch to working.
• Verify: Read REPORT.md, compare to plan. Pass or feedback.
Plan-verify IS the agent's self-check mechanism. It does all three: entry check + planning + verification.

Working checks nothing. It acts.

Three levels, not four. The brain checks agents. Plan-verify checks tasks AND outputs — it's the entry check, the planner, and the loss function, all in one role. Working just acts. No level reaches into another's business.

For P0 agents (no plan-verify), the entry check lives in the agent's own CLAUDE.md — because there's no verifier to do it. For agents with plan-verify, the entry check is plan-verify's first step.

Part X: The Communication Protocol

93. The problem: mechanism mixed with agents

Right now, brain's CLAUDE.md contains both:

Mechanism: HOW to parse intent, match domain, resolve to agent
Data: WHICH agents exist (agents.md)
Behavior: WHAT to do when matching, creating, launching

All three are mixed in one CLAUDE.md. When math-modeling needs the same routing capability for its sub-agents, it has to RE-IMPLEMENT the pattern. When a new non-leaf agent is created, it has to copy the brain's routing logic by hand.

This is the same mistake we made with plan-verify before it became infrastructure. The verification protocol was embedded in each agent. Then we extracted it into plan-verify/common/ and sync.py. Now every agent gets the protocol for free.

The communication/routing mechanism needs the same treatment: extract it, isolate it, make it reusable.

94. What communication is

Communication is how data flows between agents. It's the pipe, not the shell.

The contract: Down: TASK.md flows from sender to receiver Up: REPORT.md flows from receiver back to sender Sender describes WHAT it needs (intent), never WHO should do it. Receiver reads TASK.md, works, writes REPORT.md. Neither knows the other's name.

That's the entire protocol. The non-leaf agent decides WHERE to send (that's attention, the brain's job). Communication only defines HOW it flows.

95. The TASK.md contract

Every TASK.md, everywhere in the system: ## Intent What I need done (domain language, not agent names) ## Context What the fulfiller needs to know ## Deliverable What I expect back

This format is the same whether brain/ sends to resume-writer/, or math-modeling/ sends to algorithm-optimization/, or plan-verify/ sends to working/. One format. Any depth. Any agent type.

96. Isolation

Communication is isolated infrastructure — separate from every agent that uses it.

Four infrastructure components: brain/ attention decides WHERE to send plan-verify/ verification decides HOW WELL it was done knowledge-base/ knowledge provides WHAT to know communication/ communication defines HOW data flows Each is independent. Each has one job. No overlaps. brain: the shell (connects programs) communication: the pipe (carries data) plan-verify: the debugger (checks output) knowledge-base: the library (provides parts)

97. What agents never know

A leaf agent never knows: • Who sent the TASK.md • Who reads the REPORT.md • What other agents exist • Where in the tree it sits A non-leaf agent never knows: • The internal structure of sub-agents • How the sub-agent does the work • Other non-leaf agents at the same scope The ONLY coupling: • TASK.md format (universal) • REPORT.md format (universal)

This is Unix pipes. grep doesn't know about awk. They communicate through stdin/stdout — a universal contract. The pipe is isolated from both programs.

98. This is a specification

This document is not documentation of one implementation. It is a specification that anyone can implement.

What's universal (the spec): • Two agent types: leaf and non-leaf • Four infrastructure roles: attention, verification, knowledge, communication • The contracts: TASK.md down, REPORT.md up • The recursion: non-leaf contains leaf or non-leaf • Clean context = focused agent (aligns with model internals) What's one implementation (ours): • Filesystem as the data store • CLAUDE.md as the identity file • brain.sh as the launcher • Terminal.app as the window manager • Claude as the LLM

Someone else might implement this with:

• Database instead of filesystem • Web UI instead of Terminal windows • REST API instead of files • GPT or Gemini instead of Claude • Python framework instead of bash scripts • Docker containers instead of folders

The spec doesn't care. The principles are the same:

1. Two agent types: leaf (acts) and non-leaf (directs).
2. Four infrastructure roles, each isolated: attention, verification, knowledge, communication.
3. One contract: task down, report up. Sender describes WHAT, not WHO.
4. Recursive: non-leaf can contain non-leaf. Any depth.
5. The system activates existing knowledge, doesn't teach new knowledge.
6. Each level checks its own scope. No level reaches into another.
7. Leaf grows to non-leaf when scope pressure demands it.

Seven principles. Implementation-free. Build it however you want.
